# آزمایار — تست برنامه از روی مخزن گیت

آزمایار یک برنامهٔ محلی با رابط فارسی و راست‌چین است. آدرس مخزن عمومی را می‌گیرد، نسخهٔ مشخص کد را دریافت می‌کند و آن را در یک کانتینر موقت اجرا می‌کند. نتایج تست، خطاهای مرورگر، زمان پاسخ و مصرف منابع از خروجی واقعی اجرا ثبت می‌شوند.

**برای شروع در ویندوز، ZIP را Extract کنید و فایل `run_windows.bat` را باز کنید.** رابط در آدرس `http://127.0.0.1:8877` باز می‌شود. پنجرهٔ ترمینال را تا پایان آزمون باز نگه دارید.

## پیش‌نیازها

- Python نسخهٔ 3.11 یا جدیدتر: https://www.python.org/downloads/
- Git: https://git-scm.com/downloads
- Docker Desktop برای Windows / macOS یا Docker Engine برای Linux: https://docs.docker.com/get-started/get-docker/
- اینترنت برای دریافت مخزن، تصویر مرورگر و وابستگی‌های برنامهٔ مقصد.

در ویندوز، Docker Desktop باید روشن باشد و از **Linux containers** استفاده کند. WSL 2 و مجازی‌سازی باید طبق راهنمای Docker آماده باشند. از PowerShell با این فرمان‌ها آماده‌بودن ابزارها را بررسی کنید:

```powershell
python --version
git --version
docker info
```

اگر Python از طریق `py` اجرا می‌شود، از `py -3 --version` استفاده کنید. پس از نصب Git، پنجرهٔ ترمینال یا فایل راه‌انداز را دوباره باز کنید.

در Linux / macOS:

```bash
chmod +x run_linux_mac.sh
./run_linux_mac.sh
```

راه‌اندازی دستی:

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux / macOS:
source .venv/bin/activate
python -m pip install -r requirements.txt
python app.py
```

اگر پورت اشغال است:

```bash
python app.py --port 8878
```

## آزمون نمونهٔ دیدبان

مخزن نمونه در فرم از ابتدا قرار دارد:

```text
https://github.com/bamirreza5/Dideban
```

۱. Docker را روشن کنید و آماده‌شدن نشانگر بالای صفحه را منتظر بمانید.

۲. نوع پروژه را «شناسایی خودکار» یا `Django` بگذارید. مقدار شاخه را خالی بگذارید تا شاخهٔ پیش‌فرض استفاده شود؛ برای نمونهٔ فعلی `main` نیز درست است.

۳. گزینه‌های تست مخزن، مرورگر و فشار را روشن نگه دارید. برای شروع، ۵ کاربر HTTP و ۱۵ ثانیه کافی است.

۴. برای سناریوی ثبت مشتری، بخش تنظیمات پیشرفته را باز کنید و «نمونهٔ دیدبان» را بزنید. یا از «ورود تنظیمات»، فایل `examples/dideban.json` را انتخاب کنید. این سناریو فقط در دیتابیس موقت مشتری می‌سازد.

۵. «شروع آزمون» را بزنید. اولین بار، تصویر مرورگر و Node دانلود و ساخته می‌شود؛ این مرحله بسته به سرعت اینترنت ممکن است چند دقیقه طول بکشد. ساخت ناموفق دوباره از لایه‌های قابل استفادهٔ Docker ادامه می‌یابد.

۶. در «نتایج و خطاها» هر بررسی را باز کنید. جزئیات فرمان، خطا یا مسیر صفحه در آن ثبت می‌شود. تب «خروجی اجرا» برای پیگیری نصب و Traceback است.

۷. از گزارش HTML برای مطالعه و چاپ به PDF، از JSON برای پردازش ماشینی و از CSV برای نمونه‌های منابع استفاده کنید.

## چه چیزهایی بررسی می‌شود؟

| بخش | رفتار واقعی |
| --- | --- |
| دریافت مخزن | clone کم‌عمق، شاخهٔ انتخابی، ثبت Commit SHA و کپی بدون فایل‌های Git و دیتابیس قبلی |
| تست موجود | `manage.py test` برای Django؛ `npm test` در صورت داشتن script؛ `pytest` برای Python عمومی؛ یا فرمان اختصاصی |
| بررسی کد Python | تشخیص خطای نحوی فایل‌ها، حداکثر ۵۰۰۰ فایل |
| راه‌اندازی Django | بررسی تنظیمات، migration و ساخت حساب عادی موقت برای ورود |
| مرورگر | Chromium بدون پنجره، ورود فرم استاندارد Django، بازدید صفحات، خطاهای HTTP، استثنای JavaScript، پیام کنسول و تصاویر |
| موبایل | بررسی سرریز افقی در عرض ۳۹۰ پیکسل؛ این کار تضمین درستی کامل طراحی موبایل نیست |
| سناریوها | اجرای مرحله‌های تعریف‌شدهٔ شما و ذخیرهٔ تصویر موفقیت یا شکست |
| فشار HTTP | کاربران هم‌زمان، نرخ خطا، درخواست بر ثانیه و زمان پاسخ P50 / P95 / P99 |
| منابع | CPU، RAM و I/O فرایندهای سرور؛ آمار کل کانتینر و کل سیستم میزبان در دامنه‌های جدا |
| گزارش | HTML مستقل، JSON، CSV، تاریخچهٔ محلی و تصاویر صفحات |

تعداد «بررسی‌های موفق» برابر تعداد رکوردهای بررسی است، نه تعداد تست‌های داخلی. Django تعداد تست‌های داخلی را جدا گزارش می‌کند. برای Node و فرمان اختصاصی، اگر شمارش استانداردی موجود نباشد، تعداد ساختگی نمایش داده نمی‌شود. کد خروج صفر بدون تست کشف‌شدهٔ Django به عنوان آزمون موفق شمارش نمی‌شود.

وضعیت «تکمیل‌شده» یعنی مراحل اجرا پایان یافته‌اند؛ ممکن است گزارش آن اجرا خطای برنامه داشته باشد. «اجرای ناقص» به مشکل آماده‌سازی یا شکست ادامهٔ محیط اشاره می‌کند. هر موردِ اجرا نشده، جدا با وضعیت مناسب نمایش داده می‌شود.

## مصرف منابع را چگونه بخوانم؟

سه دامنه از هم جدا هستند:

- **برنامه مقصد:** فقط درخت فرایندهای سرور. مرورگر آزمون در آن نیست. برای CPU، صددرصد برابر یک هسته است؛ برنامهٔ چند‌هسته‌ای می‌تواند بیش از صددرصد مصرف کند. RAM مجموع RSS است و صفحات اشتراکی ممکن است چند بار شمرده شوند. فرایندهای خیلی کوتاه میان نمونه‌ها ممکن است ثبت نشوند.
- **کل کانتینر:** برنامه، نصب وابستگی‌ها، تست‌ها و مرورگر. برای CPU، صددرصد برابر یک هسته است. نمونه‌ها تقریباً هر ۳ ثانیه ثبت می‌شوند. Docker مقدار حافظهٔ خود را گزارش می‌کند که می‌تواند با RSS فرق داشته باشد.
- **کل سیستم میزبان:** مصرف کل دستگاهی که ابزار روی آن اجرا شده؛ سایر برنامه‌های شما نیز در آن هستند. CPU درصد کل ظرفیت میزبان است. در Docker Desktop، مصرف کانتینر مربوط به Linux VM است، ولی مصرف میزبان با psutil روی سیستم اجراکنندهٔ رابط گرفته می‌شود.

نمونه‌برداری برنامه تقریباً هر ۱ ثانیه است. CPU اولیه تا داشتن نمونهٔ دوم گزارش نمی‌شود. اگر دسترسی فرایند یا نمونه موجود نباشد، مقدار «نامعلوم» نمایش داده می‌شود، نه صفر. میانگین CPU میانگین نمونه‌هاست و شامل بازه‌های اندازه‌گیری‌نشده نیست.

CSV ستون `scope` و `phase` دارد تا منابع مرحله‌ها و دامنه‌ها را مقایسه کنید. `read_mb` و `write_mb` I/O تجمعی‌اند، نه سرعت لحظه‌ای. برای میزبان، مبنا ابتدای پایش آن اجراست؛ برای کانتینر، مبنا شروع کانتینر است. فیلدهای شبکه برای کانتینر و میزبان ثبت می‌شوند؛ این نسخه شبکه را به فرایندهای برنامه نسبت نمی‌دهد. واحدهای حافظه و I/O در فایل‌ها MiB هستند.

آزمون فشار، HTTP ارسال می‌کند؛ هر کاربر یک مرورگر کامل نیست. زمان پاسخ P95 یعنی دست‌کم ۹۵ درصد درخواست‌های ثبت‌شده از آن سریع‌تر یا برابر آن بوده‌اند. معیارها شامل درخواست‌های شکست‌خورده هم هستند؛ نرخ خطا و نمونهٔ خطاها را همراه آن بخوانید. پاسخ HTTP 200 که از مسیر حفاظت‌شده به صفحهٔ ورود برگشته باشد، موفقیت دسترسی به آن بخش محسوب نمی‌شود.

## سازگاری و محدودیت‌ها

- مخزن‌های **عمومی HTTPS** در GitHub، GitLab و Bitbucket پشتیبانی می‌شوند. ورود، Token، SSH، Git LFS و submodule خودکار در این نسخه وجود ندارد.
- Django همراه با `requirements.txt` یا `pyproject.toml` شناسایی می‌شود. محیط مقصد Python 3.12 تصویر Playwright است؛ پروژه‌های نیازمند نسخهٔ دیگر باید تصویر اجرا را تغییر دهند.
- Django با تنظیمات آزمایشی، دیتابیس SQLite جدید، ارسال ایمیل در حافظه و حساب عادی موقت اجرا می‌شود. پروژهٔ وابسته به قابلیت خاص PostgreSQL، Redis، Celery یا سرویس بیرونی به آماده‌سازی اختصاصی نیاز دارد. سرویس‌های خارجی به طور خودکار ساخته نمی‌شوند.
- بررسی `check --deploy` در متغیرهای محیط آزمایشی اجرا می‌شود؛ این نتیجه ارزیابی سرور واقعی یا تنظیمات تولید شما نیست.
- احراز هویت استاندارد با فرم username / password پشتیبانی می‌شود. ورود SSO، OTP، CAPTCHA و کاربران سفارشی دارای فیلد الزامی بیشتر به سناریو و دادهٔ آماده نیاز دارند. اگر مرورگر خاموش باشد، برای Django ورود HTTP استاندارد قبل از فشار امتحان می‌شود.
- Node 22 همراه npm پشتیبانی می‌شود. پروژه‌های معمول `start` یا `dev`، Vite و Next شناسایی می‌شوند. محیط مقصد یک سرور با پورت **8765** می‌خواهد. برای سایر ساختارها، `start_command` را صریح وارد کنید. Yarn / pnpm و monorepo پیچیده مسیر خودکار آماده ندارند؛ زیرپوشه و آماده‌سازی را تنظیم کنید.
- Python عمومی، Flask یا FastAPI به فرمان شروع شما نیاز دارد؛ برای مثال: `uvicorn main:app --host 127.0.0.1 --port 8765`. وابستگی‌های همین فرمان باید در پروژه موجود باشند.
- مرورگر، درخواست به CDN و API خارجی را مسدود می‌کند. این موارد به عنوان محدودیت محیط گزارش می‌شوند. برای برنامه‌ای که بدون سرویس خارجی کار نمی‌کند، mock یا محیط تست آن سرویس را آماده کنید. خود فرایند برنامه و نصب وابستگی‌ها دسترسی شبکه دارند.
- تست معنایی ثبت/ارجاع/تأیید نامه، سطح دسترسی و قوانین اختصاصی از روی آدرس Git قابل استنتاج قطعی نیست. باید در تست‌های پروژه یا سناریوهای شما وجود داشته باشد. این نسخه مدل هوش مصنوعی یا API پولی لازم ندارد و ادعای کشف همهٔ باگ‌ها نمی‌کند.
- تحلیل جامع امنیت، SQL injection، اسکن آسیب‌پذیری وابستگی‌ها و پوشش کد در این نسخه انجام نمی‌شود.

## سناریوهای اختصاصی

سناریوها آرایهٔ JSON هستند. هر سناریو یک `name` و آرایهٔ `steps` دارد:

```json
[
  {
    "name": "مشاهده فهرست نامه‌ها",
    "steps": [
      {"action": "goto", "value": "/letters/"},
      {"action": "expect_text", "selector": "h1", "value": "نامه‌ها"}
    ]
  }
]
```

عملیات قابل استفاده:

| action | پارامترها | کاربرد |
| --- | --- | --- |
| `goto` | `value` مسیر محلی شروع‌شده با `/` | باز کردن صفحه |
| `fill` | `selector` و `value` | پر کردن ورودی |
| `click` | `selector` | کلیک روی کنترل مشخص |
| `select` | `selector` و `value` | انتخاب option با value مشخص |
| `check` | `selector` | فعال کردن checkbox |
| `expect_text` | `selector` اختیاری و `value` | انتظار وجود متن در انتخابگر؛ پیش‌فرض body |
| `expect_url` | `value` مسیر کامل محلی | بررسی آدرس نهایی |

انتخابگرها CSS یا انتخابگرهای پشتیبانی‌شده Playwright هستند. انتخابگر باید یکتا باشد؛ برای نمونهٔ دیدبان، `form.form-card button[type="submit"]` استفاده شده تا دکمهٔ خروج در هدر به اشتباه انتخاب نشود. هر سناریو باید وضعیت مستقل خودش را آماده کند؛ دادهٔ سناریوی قبلی در همان اجرای موقت باقی می‌ماند. برای قواعد تجاری، بعد از عملیات حتماً `expect_text` یا `expect_url` متناسب تعریف کنید.

دکمه‌های «ذخیره تنظیمات» و «ورود تنظیمات» برای اجرای قابل تکرار و استفاده از preset هستند. هیچ رمز تولیدی را در سناریو یا فرمان نگذارید؛ تنظیمات و فرمان‌ها بخشی از گزارش می‌شوند.

## معماری و نگهداری

```text
app.py                  رابط محلی و API
qa/config.py            اعتبارسنجی ورودی
qa/engine.py            دریافت مخزن، کنترل Docker، توقف و تاریخچه
qa/report.py            گزارش مستقل و CSV منابع
worker/Dockerfile       محیط Python، Node و Chromium
worker/runner.py        تست، سرور موقت، مرورگر و فشار
web/                    رابط فارسی بدون CDN
examples/dideban.json    تنظیمات و سناریوی آمادهٔ دیدبان
tests/                  تست‌های خود ابزار
docs/VERIFICATION_FA.md  حدود راستی‌آزمایی این نسخه
data/                   خروجی محلی، بعد از اولین اجرا ساخته می‌شود
```

رابط به صورت پیش‌فرض فقط روی `127.0.0.1` گوش می‌دهد؛ آن را روی اینترنت یا شبکه عمومی منتشر نکنید. کانتینر کاربر غیر root دارد؛ بدون bind mount از پوشه‌های شخصی و بدون Docker socket اجرا می‌شود. سقف CPU، RAM، تعداد فرایند و زمان اجرا اعمال می‌شود. تنها مخازن مورد اعتماد را اجرا کنید؛ کانتینر مرز امنیتی مطلق نیست و شبکهٔ برنامه باز است.

اگر اجرای قبلی ناتمام مانده باشد، در شروع بعدی به عنوان «قطع‌شده» ثبت می‌شود. کانتینرهای باقی‌مانده را از Docker Desktop بررسی کنید؛ نام آن‌ها با `azmayar-` شروع می‌شود. دکمهٔ توقف برای بستن اجرای فعال و نگهداری شواهد موجود است. در پایان عادی، کانتینر و کپی موقت کد حذف می‌شوند، ولی گزارش‌ها در `data/<run-id>/` می‌مانند.

خود برنامه را با این فرمان تست کنید؛ این کار به موتور Docker نیاز ندارد، ولی psutil باید نصب باشد:

```bash
python -m unittest discover -s tests -v
```

برای بازسازی تصویر پس از تغییر فایل‌های worker، تصویر کش‌شدهٔ `azmayar-worker:1.0.0` را در Docker Desktop حذف کنید یا دستور زیر را اجرا کنید:

```bash
docker build -t azmayar-worker:1.0.0 worker
```

## خطاهای رایج

| مشکل | اقدام |
| --- | --- |
| نشانگر Docker آماده نیست | Docker Desktop را اجرا کنید؛ Linux containers و خروجی `docker info` را بررسی کنید |
| دریافت Git ناموفق است | آدرس اصلی مخزن عمومی را وارد کنید؛ آدرس صفحه tree / blob قابل استفاده نیست |
| دانلود تصویر یا pip ناموفق است | خروجی اجرای همان مرحله را بخوانید؛ دسترسی اینترنت و رجیستری مربوط را بررسی کنید |
| Build یا نصب بسته نیازمند کتابخانه سیستمی است | آن کتابخانه را به Dockerfile مقصد اضافه کنید و تصویر را بازسازی کنید |

| صفحه به login برمی‌گردد | حساب آزمایشی، فرم ورود و سناریوی احراز هویت را بررسی کنید |
| زمان ساخت تصویر از زمان مجاز می‌گذرد | زمان کل را افزایش دهید؛ مقدار پیش‌فرض ۲۵ دقیقه، حداکثر ۶۰ دقیقه است |
| گزینه‌ای در برنامهٔ مقصد تست نمی‌شود | مسیر صفحه را اضافه کنید و برای فرم/گردش کار، سناریو تعریف کنید |
